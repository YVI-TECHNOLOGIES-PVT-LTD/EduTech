## 1. Executive Summary

EduTrack ERP adopts an **organization-centric multi-tenant model** where `organizations` serves as the root tenant anchor (`org_id`).

However, a forensic audit of the database implementation reveals a **critical security vulnerability: multi-tenant isolation is enforced 100% at the application layer, with ZERO effective database-level isolation**.

Specifically:

1. **PostgreSQL RLS is completely bypassed or ineffective**: RLS is only defined in SQL for 2 tables (`chatbot_sessions` and `chatbot_messages`). Furthermore, the application connects to PostgreSQL using the cluster superuser (`postgres`), which natively bypasses RLS policies.
2. **Context variable `app.current_org_id` is never set**: The application backend never executes `SET app.current_org_id` on incoming database connections, rendering the two defined RLS policies permanently inoperative.
3. **15 of 33 tables lack an `org_id` column**: Child tables (such as `user_roles`, `academic_year_grades`, `sections`, `student_enrollments`, `student_parents`, `admission_documents`, `admission_decisions`, `admission_fee_payments`) have no direct tenant anchor and rely entirely on foreign-key joins.
4. **No cross-tenant foreign key constraints**: The database allows records from Organization A to be assigned to users, roles, departments, or academic years of Organization B without any constraint violation.

## 2. Row Level Security (RLS) Deep-Dive

### A. Declared RLS Policies (`08_rls.sql`)

The Stage-1 SQL DDL suite contains exactly two RLS policies in [`08_rls.sql`](file:///Users/sathish/Documents/GitHub/EduTech/apps/database/stage_1/schema/08_rls.sql):

```sql
ALTER TABLE chatbot_sessions ENABLE ROW LEVEL SECURITY;
ALTER TABLE chatbot_sessions FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation_chatbot_sessions ON chatbot_sessions
  USING (org_id = current_setting('app.current_org_id', true)::UUID);

ALTER TABLE chatbot_messages ENABLE ROW LEVEL SECURITY;
ALTER TABLE chatbot_messages FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation_chatbot_messages ON chatbot_messages
  USING (
    session_id IN (
      SELECT session_id FROM chatbot_sessions
      WHERE org_id = current_setting('app.current_org_id', true)::UUID
    )
  );
```

### B. Forensic Evaluation of Failure Modes:

1. **Missing Session Variable Injection:**
   - PostgreSQL function `current_setting('app.current_org_id', true)` reads the session parameter `app.current_org_id`.
   - A static search across the entire backend repository (`apps/backend/src/`) for `app.current_org_id`, `set_config`, or `SET LOCAL` returned **zero matches**.
   - Because the backend connection pooler never sets `app.current_org_id`, `current_setting('app.current_org_id', true)` evaluates to `NULL` for every query.
2. **Superuser / Connection Owner Bypass:**
   - The backend connects via `DATABASE_URL` as user `postgres.blvseyhzsehfwdmevtyp`.
   - In PostgreSQL, superusers and table owners automatically bypass Row Level Security unless `FORCE ROW LEVEL SECURITY` is enabled AND the user is not a superuser. Superusers bypass all policies unconditionally.
3. **Prisma Schema Misleading Comments:**
   - In `apps/backend/prisma/schema.prisma`, almost every model contains the header comment:
     `/// This model contains row level security and requires additional setup for migrations.`
   - This comment was auto-generated by `prisma db pull` because tables were created on Supabase where RLS is toggled on in the UI catalog. However, **no actual policy expressions exist in PostgreSQL for 31 of the 33 tables**.

## 4. Cross-Tenant Vulnerability Analysis (Attack Surfaces)

### Surface 1: Privilege Escalation via `user_roles`

- **Mechanism:** `user_roles` table stores `(user_id, role_id)`.
- **Flaw:** `user_roles` does not check that `users.org_id == roles.org_id`.
- **Exploitation:** If a compromised or rogue administrative user on Tenant A assigns a Tenant B SuperAdmin role to a Tenant A user, the database accepts the write.

### Surface 2: Cross-Tenant Student Enrollment & Grade Hijacking

- **Mechanism:** `student_enrollments` links `student_id` to `academic_year_grade_id`.
- **Flaw:** Neither table contains `org_id`, and no composite check exists.
- **Exploitation:** A student in School 1 can be enrolled in School 2's academic roster, granting School 1 guardians access to School 2's classes, teachers, and student directories.

### Surface 3: Fallback to Arbitrary Organization in Admission Controller

- **Mechanism:** In [`admission-document.controller.ts:65-71`](file:///Users/sathish/Documents/GitHub/EduTech/apps/backend/src/modules/admission-management/controllers/admission-document.controller.ts#L65-L71):
  ```typescript
  const defaultOrg = await prisma.organizations.findFirst({
    where: { status: 'active' },
    orderBy: { created_at: 'asc' },
    select: { org_id: true },
  });
  targetOrgId = defaultOrg?.org_id;
  ```
- **Flaw:** When an incoming request lacks explicit tenant resolution, the application silently defaults to the oldest active organization in the database.
- **Exploitation:** Unauthenticated or improperly authenticated requests leak document catalogue definitions from the primary organization.

## 6. Multi-Tenant Security Findings

### FIND-SEC-01: Inoperative Row-Level Security Architecture

- **Severity:** CRITICAL
- **Location:** [`apps/database/stage_1/schema/08_rls.sql:1-15`](file:///Users/sathish/Documents/GitHub/EduTech/apps/database/stage_1/schema/08_rls.sql#L1-L15) & `apps/backend/src/lib/prismaClient.ts`
- **Evidence:** `08_rls.sql` defines policies based on `current_setting('app.current_org_id', true)`. No backend code sets this variable. Furthermore, Prisma connects via database superuser `postgres`, bypassing RLS completely.
- **Expected Behavior:** If the architecture claims database-level multi-tenancy, database connections must run under an unprivileged role with `app.current_org_id` injected on each transaction or checkout.
- **Actual Behavior:** Database-level tenant isolation is 100% non-functional.
- **Security Impact:** A single SQL injection flaw or omitted `where: { org_id }` clause in any repository immediately exposes all tenant records.
- **Recommendation:** Document that EduTrack ERP currently relies exclusively on **Application-Enforced Multi-Tenancy**. Do not introduce partial RLS during freeze. Plan an architectural upgrade for Stage 2.

### FIND-SEC-02: Silent Fallback to Default Organization in Public Controllers

- **Severity:** HIGH
- **Location:** [`apps/backend/src/modules/admission-management/controllers/admission-document.controller.ts:65-71`](file:///Users/sathish/Documents/GitHub/EduTech/apps/backend/src/modules/admission-management/controllers/admission-document.controller.ts#L65-L71)
- **Evidence:** `AdmissionDocumentController.getDocumentTypes` contains a fallback: `prisma.organizations.findFirst({ where: { status: 'active' }, orderBy: { created_at: 'asc' } })` when `org_id` cannot be resolved.
- **Expected Behavior:** Controller must reject requests lacking tenant context with HTTP 400 Bad Request or HTTP 403 Forbidden.
- **Actual Behavior:** System defaults to the first created organization, potentially leaking metadata.
- **Security Impact:** Information disclosure across tenants.
- **Recommendation:** Refactor controller to fail closed when tenant context is missing.
